# Spec v0.4 — Contrôle audio (décodeur) — Module Companion Crestron DM NVX

> Statut : **design validé (2026-06-17)**, device-binding partiellement *gated* sur mesures labo.
> Stratégie de session : **spec + protocole labo + moteur de fade (labo-indépendant)**.
> Le device-binding (effet réel du chemin, loi du volume, mute natif) est codé **après** la fenêtre labo.

## Pourquoi

Prolonger le stack « frère & sœur » (v0.2 encodeur → v0.2.1 → v0.3 décodeur → **v0.4 audio**)
en ajoutant le contrôle **audio** du décodeur : volume (avec fade), mute. Besoin terrain :
piloter le niveau et la coupure son d'un décodeur NVX depuis une surface Companion.

## Quoi (périmètre)

**Audio seul**, côté décodeur (Receiver). Pas de routing vidéo/HDMI (reporté).

| Actions | Feedbacks | Variables |
|---|---|---|
| `set_volume(target, fadeMs?=0)` | `audio_muted` | `audio_volume` |
| `adjust_volume(delta, fadeMs?=0)` | `volume_above(seuil)` | `audio_muted` |
| `audio_mute` / `audio_unmute` / `audio_mute_toggle` *(gated labo)* | | |

## Critères de succès

1. Le moteur de fade est codé, testé unitairement contre le fake, et démontrable hors-labo.
2. La spec et le protocole labo permettent, en une fenêtre labo, de lever tous les 🔜 ci-dessous.
3. Après labo : volume + mute pilotables sur le décodeur réel, fade perçu lisse, sans rework structurel.

## Environnement cible

Companion v4.x (Node 18+), TypeScript strict. Appareil labo : DM-NVX **firmware 7.1.5259**
(la doc officielle décrit **7.3.5** → écart à surveiller, notamment pour le mute). Décodeur = `192.168.2.9`.

## Device binding — faits ancrés

Source : doc REST API officielle Crestron (miroir local `docs/crestron-api/`) + RAW
`docs/hardware-validation/raw/192.168.2.9/`.

| Élément | Chemin | Valeur / type | Confiance |
|---|---|---|---|
| **Volume** | `Device.AudioVideoInputOutput.Outputs[0].Ports[0].Audio.Volume` | entier **-100..100**, *« gain of the audio output »*, défaut **0 = unité** | ✅ documenté officiel |
| **Mute** | `Device.AudioVideoInputOutput.Outputs[0].Ports[0].Audio.Mute` | booléen | ✅ documenté (exemple JSON officiel) — 🔜 confirmer sur 7.1.5259 |
| Lecture état | même objet via `GET /Device/AudioVideoInputOutput` | — | ✅ |

**Écartés (ne pas bâtir dessus) :**
- `Device.StreamReceive.Streams[].Volume` : vu dans le RAW mais **non documenté** (la doc officielle
  StreamReceive ne liste que `AudioChannels`/`AudioFormat`/`AudioMode`, lecture seule). Vestige présumé.
- `/Device/AudioControl` (`AudioVolume` 0-100) : endpoint **spéculatif** de la doc d'origine, **absent** du RAW réel.
- `NaxAudio.NaxTx…IsMuted` : côté flux **émis** (TX), hors périmètre décodeur.

**Conséquence architecture** : `/Device/AudioVideoInputOutput` **n'est pas pollé** en v0.3 → ajouter un
aux endpoint au poll, en réutilisant la machinerie poll + garde `Processing` + `post()` de
`src/panels/decoder.ts` (pattern frère & sœur). La réutilisation directe du `streamReceiveBody` de v0.3 **tombe**
(mauvais chemin).

## Moteur de fade — design (labo-indépendant, codable maintenant)

Le NVX **n'a pas de fade natif** (aucun champ `fade`/`ramp`/`duration` sur le chemin volume, doc + RAW).
Le fade est **fait côté module** = N POST de volume échelonnés. Fonction pure, isolée, testable contre le fake.

**Algorithme :**
- `nbPas = max(1, ceil(fadeMs / MIN_STEP_MS))` — `MIN_STEP_MS` défaut **100 ms** (prudent ; affiné au labo
  par la mesure du débit POST max).
- `pas = (cible - courant) / nbPas`, clampé à `[-100, 100]`, arrondi entier, posé à `actualPeriod = fadeMs / nbPas`.
- **Loi de rampe** : **linéaire en unités device** par défaut. Hypothèse sourcée : le champ est un *« gain »*
  symétrique (−100..100, 0=unité) → probablement **dB-like** → une rampe linéaire est perçue régulière
  (loudness ≈ log). 🔜 à confirmer au labo ; si la mesure montre une échelle **linéaire en amplitude**,
  basculer en répartition **log/dB** — changement **isolé dans une seule fonction** `distributeSteps()`.
- `fadeMs=0` (défaut) = **instantané** : un seul POST, pas de rampe.
- **Annulation sur nouveau réglage** : tout nouvel ordre de volume annule la rampe en cours
  (pas de fades concurrents).
- **Stop propre** sur déconnexion / `destroy()`.
- **Avertissement** (log) si `|pas|` dépasse le seuil de granularité perceptive (≈ 1 unité si 1 unité≈1 dB)
  → la durée demandée est trop courte pour la plage : fade intrinsèquement saccadé au débit réseau.

**Seuils perceptifs (recherche sourcée, fixent l'exigence indépendamment du device) :**
- Taille de pas cible **≤ 1 dB** (zipper audible au-delà ; JND loudness ≈ 0,5–1 dB → inutile d'aller plus fin).
- Période cible **≤ 50 ms** (33 ms optimal). Notre plancher HTTPS (~33–100 ms/pas) est dans la zone acceptable.
- Loi : répartir en **dB (log)** sauf si la valeur device est déjà en dB (rampe linéaire alors suffisante).
- Implication clé : le pas est piloté par le **delta de volume**, pas par la durée seule.
  `adjust_volume(-10, 2000)` à 50 ms/pas = 40 pas = 0,25 dB/pas → lisse. Un fade *court* sur une *grande*
  plage dépasse 1 dB/pas → saccadé inévitable au débit réseau → avertir.

## UX — échelle

Exposer le **gain -100..100 brut** (0 = unité), sans conversion : champs des actions, variable `audio_volume`,
seuil de `volume_above`. Honnête, zéro remap trompeur. (Le remap 0-100 serait ambigu sur un gain centré tant
que la loi n'est pas mesurée.)

## Protocole labo (livrable — à exécuter pendant la fenêtre matériel)

> **Pré-requis transverse — Étape 0** : obtenir un **flux audio réellement décodé** sur `.9`
> (`AudioFormat == Lpcm`, `CodecReady: true`, `NumAudioPacketsRcvd > 0`). Aucune capture existante ne
> l'atteint ; sans audio qui sort du HDMI, rien ci-dessous n'est mesurable.

| # | À mesurer | Méthode | Lève |
|---|---|---|---|
| 1 | **Effet réel du Volume** | flux audio actif → `POST …Outputs[0].Ports[0].Audio.Volume = 50` → écouter la sortie HDMI + `GET` pour confirmer la valeur retenue | quel chemin agit |
| 2 | **Loi de l'échelle** (dB vs amplitude) | poser 0, ±25, ±50, ±100 (et hors-borne ex. 200, -200) → écouter la progression + `GET` après chaque POST (révèle clamp/min/max) | loi de rampe du fade |
| 3 | **Mute natif sur 7.1.5259** | `POST …Audio.Mute = true/false` → écouter ; si sans effet, chercher dans l'UI web NVX (capturer la requête réseau du bouton mute) | mute natif vs repli `Volume:0`+restauration |
| 4 | **Débit POST max** | rafales de N `POST Volume`/s croissantes jusqu'à saturation/erreur | fixe `MIN_STEP_MS` |
| 5 | **`StreamReceive.Volume` inerte ?** | `POST StreamReceive.Streams[0].Volume` audio actif → vérifier qu'il ne change **rien** | confirme l'abandon du chemin non documenté |
| 6 | **Confirmer absence de fade natif** | relire la doc API 7.3.5 sur le chemin retenu (champs write-only ?) | confirme fade module-side |

**Décision Didier requise si** : aucun mute natif en 7.1.5259 → choisir entre `audio_mute = Volume:0`+restauration
(côté module) ou retirer le mute de v0.4.

## Tests

- **Fake étendu** : ajouter le sous-objet `AudioVideoInputOutput.Outputs[0].Ports[0].Audio` (`Volume`, `Mute`)
  construit depuis la structure des RAW (`Device_AudioVideoInputOutput.json`), servi par le fake device HTTPS.
- **Tests unitaires moteur de fade** : calcul nbPas/pas, clamp, arrondi, `fadeMs=0` (1 POST), annulation
  sur nouvel ordre, stop sur déconnexion, avertissement pas-trop-grossier.
- **Journey / UAT** : ajouts **différés** jusqu'à binding confirmé au labo (on ne scénarise pas un comportement
  device non mesuré).

1. **Hors-labo (cette session)** : spec (ce doc) + miroir doc + moteur de fade + fake étendu + tests unitaires.
