# v0.3 Decoder (`StreamReceive`) — Design

**Date** : 2026-06-15
**Statut** : validé (brainstorming Didier)
**Branche** : `feature/v0.3-decoder` (depuis `feature/v0.2-encoder`)
**Portée** : panneau décodeur complet — routing par URL, multicast et découverte (connect-by-name) — + généralisation du contrat `Panel` en multi-endpoint.
**Source de vérité données** : `docs/hardware-validation.md` §7 + captures `raw/192.168.2.9/` (Receiver), `raw/192.168.2.10/` (Transmitter), `raw/192.168.2.11/` (E30) + recherche doc Crestron 7.3.5 (2026-06-15).

---

## 1. Contexte & problème

v0.2 a livré l'**encodeur** (`StreamTransmit`) et la **fondation panneaux** (registre + `poll()` généralisé + détection de capacité/mode), validée 14/14 contre le fake device. v0.3 ajoute le **décodeur** : pointer un Receiver NVX sur sa source et démarrer/arrêter la réception.

Le décodeur introduit deux nouveautés structurelles par rapport à l'encodeur :

1. **Le routing est gouverné par un mode** (`SessionInitiation`), pas par un simple champ.
2. **La découverte** (`DiscoveredStreams`) exige qu'un panneau lise **deux endpoints** — ce que le contrat `Panel` mono-endpoint actuel ne sait pas faire.

**Principe directeur (inchangé, workflow device-rare)** : aucun chemin JSON deviné. Tout est ancré sur la capture réelle ou la doc citée ; ce qui reste incertain est **marqué hypothèse** et confirmé au labo.

---

## 2. Décisions validées (brainstorming)

1. **Périmètre full** : URL + Multicast + Discovery (connect-by-name) dans v0.3.
2. **UX découverte** : dropdown des streams découverts **+** option « Custom » en **texte libre acceptant variables/expressions Companion** ; résolution `nom → coordonnées` **au press** (late-binding sur le poll le plus frais).
3. **Transport gouverné par `SessionInitiation`** (confirmé doc, voir §5) — pas un xor de champs indépendants : on choisit un mode, on renseigne la coordonnée du mode. Actions séparées pour l'ergonomie, chacune écrivant **mode + coordonnée atomiquement**.
4. **`connect_to_stream`** : **multicast par défaut, URL en repli** (si l'entrée découverte a une `MulticastAddress`, mode Multicast ; sinon `RtspUri`/ByReceiver).
5. **Contrat `Panel` généralisé multi-endpoint** (option (a)) : fondation qui ressert en v0.4 (`AudioVideoInputOutput` + `NaxAudio`) et v0.5 (`DeviceSpecific` + `DeviceOperations`).
6. **Tous les champs texte d'action** : `useVariables: true` (résolution via `parseVariablesInString` au press).

---

## 3. Fondation : contrat `Panel` multi-endpoint (option (a))

Aujourd'hui (`src/panels/types.ts`) : un `Panel` déclare `endpoint: string`, et `poll()` fait un GET puis appelle `readVariables(json)`. Le décodeur a besoin de `StreamReceive` (primaire) **+** `DiscoveredStreams` (auxiliaire, alimente le dropdown et le reverse-lookup `rx_stream_name`).

**Généralisation** (le primaire garde l'identité gate/parse ; les auxiliaires sont du contexte lu par le panneau) :

```
interface Panel {
  id: string
  endpoint: string                 // primaire — pilote gate + identité du panneau
  auxEndpoints?: string[]          // NEW — endpoints additionnels pollés avec le primaire
  gate(ctx): boolean
  variableDefinitions
  readVariables(primary, aux?)     // NEW signature — aux: Record<endpoint, json>
  buildActions(api): …
  buildFeedbacks(state): …
  buildPresets?(): …
}
```

- `poll()` (dans `main.ts`) itère les panneaux actifs et, pour chacun, fetch `endpoint` + tous les `auxEndpoints`, passe le primaire et la map auxiliaire à `readVariables`. La détection de déconnexion/`scheduleReconnect` existante (`main.ts`) **enveloppe tous les GET** — aucune duplication d'orchestration.
- Rétrocompat : `auxEndpoints` absent → comportement v0.2 inchangé (l'encodeur et device-info ne sont pas touchés ; `readVariables` ignore le 2ᵉ argument).
- Chaque endpoint est parsé en **sentinelle-safe** (`subsystemObject`) : un auxiliaire absent/`"UNSUPPORTED PROPERTY…"` → la fonctionnalité dépendante dégrade (dropdown vide, `rx_stream_name` non résolu) **sans crash**.

> La signature exacte (`auxEndpoints: string[]` vs structure nommée) est un détail que l'architecte fige au plan ; l'intention — primaire + auxiliaires pollés par la boucle commune — est arrêtée.

## 4. Panneau décodeur (`src/panels/decoder.ts`)

Miroir de `encoder.ts`, avec helper `streamReceiveBody(index, props)` (POST positionnel `Streams[0]`, contrat `hardware-validation.md` §4.2).

```
id: 'decoder'
endpoint: '/Device/StreamReceive'
auxEndpoints: ['/Device/DiscoveredStreams']
gate: (ctx) => ctx.role === 'Receiver'
```

### 4.1 Actions (write path)

Toutes via `api.postSetPartial(streamReceiveBody(0, …))` ; champs texte en `useVariables: true` (résolus au press).

| Action | POST `streamReceiveBody(0, …)` | Note |
|---|---|---|
| `set_source_url(url)` | `{ SessionInitiation: 'ByReceiver', StreamLocation: <url résolu> }` | unicast RTSP |
| `set_source_multicast(address)` | `{ SessionInitiation: 'Multicast via RTSP', MulticastAddress: <addr résolue> }` | multicast |
| `connect_to_stream(stream, custom)` | résout → si `MulticastAddress` : mode Multicast ; sinon `RtspUri`/ByReceiver | dropdown + Custom (voir §4.4) |
| `enable_stream` | `{ Start: true }` | garde `Processing` (§6) |
| `disable_stream` | `{ Stop: true }` | |

`SessionInitiation` : on écrit **les chaînes observées sur le device** (`"ByReceiver"`, `"Multicast via RTSP"`) plutôt que la forme doc (`"Multicast"`) — preuve la plus forte (§5, hypothèse #2).

### 4.2 Variables (`readVariables(streamReceive, { DiscoveredStreams })`)

Lecture sentinelle-safe depuis `StreamReceive.Streams[0]` + la map découverte :

| Variable | Source |
|---|---|
| `rx_source_url` | `Streams[0].StreamLocation` |
| `rx_multicast_address` | `Streams[0].MulticastAddress` |
| `rx_session_initiation` | `Streams[0].SessionInitiation` |
| `rx_status` | `Streams[0].Status` (`"Stream Stopped"` au repos) |
| `rx_resolution` | `${HorizontalResolution}x${VerticalResolution}` |
| `rx_processing` | `Streams[0].Processing` (bool) |
| `rx_stream_name` | **reverse-lookup** : matche la source courante (URL ou multicast) dans `DiscoveredStreams` → `SessionName` (le `StreamReceive` n'a pas de champ nom ; la découverte le fournit) |
| `rx_discovered_count` | nb d'entrées `DiscoveredStreams.Streams` |
| `rx_discovered_names` | liste des `SessionName` (aide l'opérateur en mode Custom) |

### 4.3 Feedbacks (depuis `state()`)

| Feedback | Règle |
|---|---|
| `rx_receiving` (bool) | réception active. Heuristique de repli : `rx_status !== 'Stream Stopped' && rx_processing !== true` — la chaîne « active » exacte est une hypothèse labo (§7-#1) |
| `rx_source_matches(value, by)` | compare la source courante à une valeur ; `by` ∈ {`url`, `multicast`, `name`} |
| `rx_processing` (bool) | device en transition (utile pour griser un bouton pendant `Processing`) |

### 4.4 `connect_to_stream` — dropdown + Custom

- Options : un **dropdown** dont les `choices` = `[{ id: <SessionName|UniqueId>, label: <SessionName> }, …]` issus du dernier `DiscoveredStreams`, **plus** une entrée `{ id: 'custom', label: 'Custom (formule)…' }`.
- Un `textinput` `useVariables: true`, **visible seulement** si le dropdown vaut `custom` (`isVisible`).
- **Rafraîchissement** : quand le poll détecte un changement de `DiscoveredStreams` (set de `SessionName` modifié), re-`setActionDefinitions()` (full-replace, supporté — mémoire `sdk-companion`). Débounce/diff pour éviter le churn à chaque poll inchangé.
- **Résolution au press** :
  1. si valeur = `custom` → résoudre l'expression (`parseVariablesInString`) en chaîne ; tenter de matcher contre un `SessionName` découvert ; sinon traiter comme URL/multicast brut.
  2. sinon → retrouver l'entrée découverte par id → préférer `MulticastAddress`, sinon `RtspUri`.
  3. écrire le couple `SessionInitiation` + coordonnée correspondant (§4.1).

### 4.5 Presets — section « Decoder »

Miroir de l'encodeur : `dec_start_rx` (porte le feedback `rx_receiving`), `dec_stop_rx`, `dec_set_source_url`, `dec_set_source_multicast`, `dec_connect_stream` (dropdown vide par défaut).

## 5. Modèle `SessionInitiation` (confirmé doc Crestron 7.3.5)

Recherche doc (2026-06-15) — `StreamReceive` schéma v2.0.1 :

- **`StreamLocation` est WRITABLE côté Receiver** (≠ Transmitter read-only). Source URL RTSP cible.
- **`SessionInitiation` gouverne le mode** (writable), 3 valeurs :
  - `ByReceiver` → unicast RTSP, le décodeur tire depuis `StreamLocation`
  - `Multicast` (observé `"Multicast via RTSP"`) → le décodeur écoute `MulticastAddress`
  - `ByTransmitter` → push (l'encodeur initie) — **hors périmètre v0.3** (rare)
- **`Start`/`Stop = true` writable côté RX** depuis schéma v2.0.1 ; notre `.9` est en `Version "2.0.1"` → supporté.
- **Pas de routing par UUID/nom** : on extrait `RtspUri`/`MulticastAddress` de `DiscoveredStreams` et on les écrit dans `StreamLocation`/`MulticastAddress`. Le `connect_to_stream` est donc une **résolution**, pas un binding natif.

Sources : `StreamReceive.htm`, `DiscoveredStreams.htm`, `StreamTransmit.htm` (sdkcon78221.crestron.com, schémas datés juin 2026).

## 6. Robustesse / gestion d'erreurs

- **Flag `Processing`** (read-only) : attendre `Processing === false` **avant** d'envoyer une commande au décodeur (règle de prudence documentée). Les callbacks d'action vérifient l'état poll le plus frais ; si `Processing`, log + abandon propre (l'action signale l'attente, pas un échec dur).
- **`StatusId`** : POST → lire `Actions[].Results[].StatusId` (`0`=OK, autre=erreur loggée) — déjà géré côté `api.ts` depuis v0.2.
- **Sentinelle / absence** : `StreamReceive` ou `DiscoveredStreams` peut être `"UNSUPPORTED PROPERTY, CHECK REST API!!!"` (E30) ou absent → `subsystemObject()` → N/A sans crash. Le gate `role === 'Receiver'` évite déjà le cas E30, mais le parsing reste défensif.
- **Adressage par POSITION** : `Streams[0]`, jamais par UUID (UUID volatils, `hardware-validation.md` §6.4).
- **Reconnexion** : une bascule de mode (reboot) est rattrapée par la reconnexion existante qui re-détecte le rôle et recompose les panneaux (archi §4.1).

## 7. Hypothèses portées en code offline (à confirmer au labo)

1. **Chaîne `Status` de réception active** : seul `"Stream Stopped"` (repos) est connu. Feedback `rx_receiving` codé avec heuristique de repli ; valeur active à cartographier au labo (GET dans différents états).
2. **Chaînes `SessionInitiation` en écriture** : on écrit les valeurs observées (`"ByReceiver"`, `"Multicast via RTSP"`) ; confirmer que le device les accepte/normalise (la doc cite `"Multicast"`).
3. **Timing du flag `Processing`** : règle « attendre `false` » documentée, comportement exact (durée, transitions) à observer.
4. **`Start`/`Stop` côté RX** : confirmés par schéma doc v2.0.1 — à valider empiriquement (POST réel).

Conformément au workflow device-rare : code écrit contre fixtures avec hypothèses **marquées**, jamais présentées comme faits ; l'UAT labo confirme que le live = la fixture.

Étendre `scripts/uat/fake-device/server.ts` :

- Prouve la chaîne **WRITE bouton → module → device → oracle** sans labo.

### 8.2 Tests offline (`node:test`, fixtures depuis `raw/`)
- `readVariables(.9 StreamReceive, .9 DiscoveredStreams)` → état attendu (source vide, status repos, count discovery = 2, names attendus).
- `gate`: `role==='Receiver'` → actif ; `'Transmitter'` → inactif ; sentinelle E30 → N/A sans crash.
- `connect_to_stream` : résolution `SessionName → MulticastAddress` (préférence) et repli `→ RtspUri` ; Custom (expression) → résolution.
- Forme du body positionnel `streamReceiveBody(0, …)` (longueur 1, props sur `[0]`).

## 9. Hors périmètre v0.3

- Mode `ByTransmitter` (push) — rare, non couvert.
- Bascule de mode Encoder↔Decoder (reboot) — **v0.5**.
- Audio/volume/HDMI du flux reçu — **v0.4** (`AudioVideoInputOutput`).
- Sélection d'un stream secondaire (`Streams[1..3]`) — non requis ; on cible `Streams[0]` (primaire).

---

## 10. Critères de succès

- Panneau décodeur actif **uniquement** quand `role === 'Receiver'` ; sentinelle E30 ne crashe pas.
- Routing URL, multicast et connect-by-name fonctionnels contre le fake Receiver (oracle WRITE prouvé).
- Aucun chemin JSON non adossé à `hardware-validation.md` §7 ou à la recherche doc §5.
- Contrat multi-endpoint généralisé sans régression sur l'encodeur v0.2 (tests v0.2 toujours verts).
- Hypothèses §7 toutes marquées et listées pour le créneau labo.
